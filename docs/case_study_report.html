1. Business Scenario & Core Workflow

An industrial manufacturing and supply company sells engineered equipment and heavy machinery parts to B2B clients. To manage business sales without the bloat of an off-the-shelf enterprise solution, this application implements the critical operational sequence:

1. Enquiry
Customer & Line Items
→
2. Quotation
Discounts & Taxes
→
3. Sales Order
1-to-1 conversion
→
4. Reservation
Admin locks stock
→
5. Dispatch
Stock deducted

Workflow Lifecycle Rules

  • Customer Enquiry: Captures complete company profile (Company Name, Contact Person, Mobile, Email, City) and demanded industrial products with required dates and notes. Status pipeline: NEW → QUOTED → WON / LOST.
  • Quotation Engine: Generated against an enquiry. Evaluates Base Price, Trade Discount %, and Statutory GST % per line item. The Grand Total is computed and strictly validated on the backend. Status pipeline: DRAFT → SENT → ACCEPTED / REJECTED. When marked ACCEPTED, the associated Enquiry automatically transitions to WON.
  • Sales Order Conversion: Only ACCEPTED quotations can be converted. DRAFT and REJECTED quotations are rejected with HTTP 400. A strict relational UNIQUE constraint on quotation_id prevents duplicate orders from ever being generated.
  • Inventory Reservation: Admin confirms a pending Sales Order. System checks that demanded quantity does not exceed available stock. Physical inventory does not decrease during reservation; only Reserved stock increases.
  • Dispatch: Admin enters vehicle number and driver name. Upon dispatch, both Physical Quantity and Reserved Quantity decrease atomically, keeping the net available quantity unchanged.

The system uses strict PostgreSQL relational modeling across 12 normalized tables. No workflow state is hidden inside loose unstructured JSON blobs.

Zero-Setup Database Architecture: The application supports standard PostgreSQL connection strings via DATABASE_URL, and seamlessly falls back to @electric-sql/pglite (genuine PostgreSQL 16 compiled to WebAssembly) so that developers, CI pipelines, and evaluators can run the entire system with zero external configuration!

4. Solving the Backend Concurrency Challenge

The Concurrency Race Condition: Available inventory = 100. Two requests arrive simultaneously:
• User A demands 80 units.
• User B demands 50 units.
Combined demand is 130 units > 100 available units. A naive client-side check or read-modify-write without locking will allow both requests to read 100 available stock, causing overselling and corrupting inventory.

The Database-Level Solution

  1. Pessimistic Row-Level Locking (SELECT ... FOR UPDATE): When an Admin confirms a Sales Order, the backend begins a PostgreSQL transaction. It queries the target inventory rows using SELECT ... FOR UPDATE with deterministic ordering (ORDER BY product_id ASC to prevent deadlocks).
  2. Serialization of Concurrent Requests: The first request acquires an exclusive lock. It computes:
    Available = Physical − Reserved − Damaged
    Since 80 ≤ 100, it executes UPDATE inventory SET reserved_quantity = reserved_quantity + 80 and commits. Available drops to 20.
  3. Safe Rejection: The second request was paused waiting on the row lock. Once Request A commits, Request B awakens and reads the freshly committed row (Physical = 100, Reserved = 80, Available = 20). Since 50 > 20, the transaction rolls back and returns HTTP 400 Bad Request: "Insufficient available inventory for Industrial Product. Required: 50, Available: 20".
  4. Hardware-Enforced Check Constraint: Even if raw SQL bypassed the code, PostgreSQL's table-level check constraint CHECK (reserved_quantity + damaged_quantity <= physical_quantity) physically prevents negative available quantities.

7. Live Verification Round Defense Readiness

The case study highlights that shortlisted candidates will receive an unannounced change during live verification. Our architecture already contains built-in solutions for both anticipated scenarios:

Scenario A: Add "DAMAGED" Stock Bucket

Available Quantity = Physical Quantity − Reserved Quantity − Damaged Quantity

Implementation: The inventory table already incorporates damaged_quantity NUMERIC DEFAULT 0 and the check constraint CHECK (reserved_quantity + damaged_quantity <= physical_quantity). The API and frontend live stock modal already support viewing and modifying damaged stock.

Scenario B: Cancel Confirmed Sales Order & Release Reserved Inventory

Implementation: Endpoint POST /api/sales-orders/:id/cancel is implemented in salesOrders.routes.js. When triggered on a CONFIRMED order, an atomic transaction decrements reserved_quantity by each item's quantity, returning the reserved stock back to available inventory.
